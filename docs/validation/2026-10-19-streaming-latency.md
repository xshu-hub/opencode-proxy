# 2026-10-19 无推理预热、热池与流式延迟回归

范围仅为 OpenCode 代理，基于 `0b2138f` 及当前协议兼容工作树。全部推理经过真实全局 OpenCode，未修改 OpenCode 或直接调用供应商。配置、原始报告及 DSH 文件索引位于系统临时目录，不进入 Git。

## 实现

- 网关启动后异步加载目录并预热原生服务、MCP 和插件，预热不创建模型推理请求。初始目标可由 `warmupModels` 指定；空列表选择已启用模型，按实际请求更新最近使用目标，同模型别名不重复占位。
- 最多保留 `maxIdleWorkers` 个空闲进程，默认 2 个。当前热目标不因普通空闲计时退出，其他进程仍按 `workerIdleMs` 退出；执行中的推理不受空闲容量限制，默认并发仍无限。正常短请求复用现有进程，不额外启动随后被淘汰的备用进程。
- 完成事件、usage 和 EOF 不等待中止确认、会话删除、实例重置或临时文件清理。清理成功后才可重新租用进程；失败则丢弃。下一请求可取消等待即将就绪的进程，额外并发请求仍能冷启动专属进程。关闭时等待后台回收。
- 原生工具 pending 事件先返回客户端工具 ID/名称，完整 JSON 到达后再返回参数。支持 Chat、Responses、Messages 对应的事件生命周期；没有伪造逐字参数，也未改变客户端执行工具的边界。
- 成功 SSE 立即刷新响应头，空闲时发送注释心跳，设置 `no-transform` 和 `X-Accel-Buffering: no`，保留背压和断连取消。首个有效输出前不预发 HTTP 200，继续保留真实错误状态。

## 测量方法

Windows，全局 OpenCode 1.18.0，DSH 0.2.1-alpha.5 原生 DeepSeek Messages 适配器。测试模型为 `deepseek-flash`、`deepseek-v4-pro`。DSH 自身使用 Messages，本记录没有把 DSH 描述为三协议客户端；其余三协议通过网关真实 HTTP 分别调用。

运行 `npm run test:live:latency`，使用相同的固定 8 行文本提示、关闭思考和 1024 输出上限。优化前代码完整复制到临时快照；优化后也使用冻结快照，避免运行期间代码变动。两个阶段不与集成或其他模型回归并行运行。
优化后通过 `warmupModels` 明确选择这两个 DeepSeek 模型；旧版本尚未接入自动预热，该初始目标列表不会改变其冷启动行为。

- 每模型/客户端 3 次新网关立即首请求，以及对应的 3 次复用请求。复用测量在后台清理完成后开始，代表就绪进程的延迟；紧邻请求等待清理的正确性另由阻塞重置的真实 OpenCode 测试验证。
- 另测 1 次就绪后的首请求，单独记录就绪耗时。旧代码没有自动预热，因此其就绪等待约 1 毫秒，首请求仍是冷启动；新代码等待两模型无推理预热完成。
- 首字从客户端发起调用到首个真实正文增量。HTTP 响应头、SSE 外壳和心跳不作为首字。记录每段文本、最大相邻间隔、结束事件与 EOF；DSH 从其实际适配器事件测量。
- 每组仅 3 次，P95 为小样本最大值；就绪首请求只有 1 次，不是稳定分位数。供应商和网络随时间波动，数字只代表本次观察，不承诺服务 SLA。预热成本单列，不计入就绪后首字。
